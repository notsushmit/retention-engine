# Scoring API

Generated by `python -m retention.api write-docs` from configs/serving.yaml and the response schemas. Do not edit by hand; tests/test_scoring_docs.py checks that this file equals a fresh build.

> The service replays 2016 KKBox data; there is no live source.
> Customers expiring more than 30 days ahead (22% of active customers on 2016-11-01) get no score.
> Plans exist for two dates only (2016-10-01 and 2016-11-01) and were built from the 30-day probability before the ordering fix.
> KKBox backtest figures are model estimates under assumed effects, not observed outcomes.

## Endpoints

### GET /health

Fields: `ready`, `store_date`, `replay_progress`, `model_checksums_match`, `config_sha256`, `valkey_reachable`, and `reason` (not registered; see below). It answers 503 with the reason when the service is not ready.

### POST /score

Request: `msno` (required) and `as_of` (optional). Features come from the service's own store; callers never post feature values.

Answers: `scored`, `outside_population` (codes `segment_trial_only`, `segment_promo_only`, `expiry_beyond_30_days`, `unseen_level:<feature>`, and `unseen_level:hidden_feature` under amendment A5) or `not_active`.

Errors:

- 404: unknown customer
- 422: malformed input
- 409: as_of differs from the store's date
- 503: not ready; a model checksum mismatch stops startup and /health says why

### GET /at-risk

Parameters: `horizon` (one of 7, 30, 59; default 30), `limit` (default 50, at most 1000), `offset`, and the filters `auto_renew`, `in_plan`. Anything else is a 422.

Order: final probability at the horizon, descending; ties by msno. Plan cell: strategy optimizer, scenario base, budget 5,000.

Every plan field reads "plan built from the 30-day probability before the ordering fix". Header note: "Ranking uses the final probability; plan membership comes from the Phase 7 plan." A date without a plan reads "no plan for this date".

### GET /alerts

Kinds: trend, event. A trend alert is shown when the registered rule holds: week start + 37 days on or before the store's date. Every trend alert carries the labels "exploratory", "false-alarm rate not validated", "detected in hindsight on the series through 2016-12-19", and its stored data-quality flags. The dimensions registered in api.alerts.trend.hidden_dimensions are removed from top_segments, too_small_segments (amendment A7) and dimension_totals, and the number removed is shown. Each cancel event reads "a cancel row, not a change in risk".

### GET /summary, GET /plans, GET /model

The dashboard's aggregates. None takes a parameter (anything else is a 422) and no customer ID appears in any of them; each body is scanned with no exemption. Two more files are pinned beside the plans and alerts files: data/processed/kkbox/sample_020/optimize/summary.parquet, data/processed/kkbox/sample_020/serving/calibration_before_after.json; a missing or differing file refuses startup.

/summary needs a ready store (503 otherwise, as /at-risk). It serves the stored /at-risk header counts with the share of active customers expiring more than 30 days ahead; three expected counts over every scored customer, from the final probabilities: days 1 to 7 (math.fsum of p7), days 8 to 30 (math.fsum of (p30 - p7) per customer) and days 31 to 59 (math.fsum of (p59 - p30) per customer, a demonstration, as every 59-day probability), labelled "expected counts from the final probabilities, scored customers only"; and, at 7 and 30 days, each customer once, by raising_1, the first group the model lists as raising the probability; "no group listed" when none is listed, counted among the 1,000 scored customers ranked highest at the horizon, in the /at-risk order (final probability descending, ties by msno), by main segment and for both together. A cell with fewer than 20 customers is suppressed, and the number suppressed is shown; there is no secondary suppression. A group or segment whose name holds a hidden dimension or a never-used word is removed and counted, as for the alerts (amendment A7). Computed once per store date.

/plans needs a ready store (503 otherwise); the store's date picks the rows. It serves the pinned summary.parquet, scenario base, the store's date; every strategy in the file for that date (optimizer, highest_risk, highest_assumed_uplift_x_value, random, fixed_action_reminder, no_action) at every registered budget level (configs/actions.yaml budget.levels). Values are served as stored; the random strategy also carries its p2_5 and p97_5 spread. Every answer carries "precomputed in Phase 7 from the 30-day probability before the ordering fix; not re-planned", the registered comparison caption, the effect prefix "Under the assumed relative base effect", effect_basis "assumed", the instability note, the no-estimate line and the two-dates disclaimer. Nothing is re-planned.

/model (answers while the store is empty): the registered model, its version, the eight files and their SHA-256, the config SHA-256, whether the model files still match, and the calibration table before and after the ordering fix at 7 and 30 days ("descriptive, no pass mark; selection half of 2016-10-01, P2 main; 2016 outcomes only"; "no 59-day row: its calibration was judged only in the Phase 3 59-day demonstration"), with "drift: not monitored (Phase 10)" and retraining "none in this phase (Phase 10)".

The step 8 latency figure was measured before the 1.5 GiB memory limit and before these three endpoints were added.

### GET /drift, and two additions to GET /model

GET /drift takes no parameter (anything else is a 422) and needs nothing from the store. It serves the file ops/drift_latest.json in the ops folder (R1 writes it); read at each call, at most 1 MB; the file is not pinned, so the body carries its own SHA-256 as `report_sha256`. Without a usable file it answers 200 with status `not monitored` (file missing) or `unreadable` (too big, not valid, naming a never-used word or holding a customer-ID-shaped string) and the sentence "drift: not monitored (Phase 10)", and no number. A column whose name holds a never-used word is removed before the body is built and counted in `hidden_by_rule`; the never-used attributes are never compared. Every body carries "Drift on replayed 2016 data: it demonstrates the mechanism, not that monitoring is effective in operation." The file is written by the drift run; it holds no customer ID, no per-customer value and no outcome.

GET /model carries two additions. `drift` reads "drift: see GET /drift (replayed 2016 data; mechanism demonstration)" when a valid drift file is present and "drift: not monitored (Phase 10)" otherwise. `last_retrain` is null until the retraining flow has written its file, and then holds the run date, the decision ('registered as candidate' or 'current model left in place'), the 30-day AUC of the candidate and of the current model with the interval of their difference, and the statement that the serving alias is unchanged, with "The comparison demonstrates the retraining mechanism only: one month decides it, and that month has a 7-day excess in its zero-paid group that is not explained."

The ops folder is mounted read-only (the ops folder (data/processed/kkbox/sample_020/ops, or its synthetic equivalent in the demo profile) read-only into the api container; nothing else under data/).

## Amendments A5 to A8

- A5 (2026-10-21, amends contract.outside_population.codes): an unseen level in a feature whose name contains a never-used attribute as a whole word (the response scan's own test) reads `unseen_level:hidden_feature`; for any other feature the code names the feature, `unseen_level:<feature>`.
- A6 (2026-10-21, amends contract.never_in_any_body, step5.scan): only the value of the msno field of a /score body and the row ID (msno) of each /at-risk row, and only when that value equals the requested customer's own ID or the listed customer's own ID; every other field and key of every response, the same string in any other field, another customer's ID in the msno field, and every error body are scanned in full. An identifier exemption, not a relaxation of the never-used rule. 3 of 425,520 known IDs contain one never-used word as a whole word; 5 of 1,474,743 distinct IDs across the seven tables do (distinct IDs, not table rows).
- A7 (2026-10-21, amends api.alerts.trend.hidden_dimensions): the hidden dimensions are also removed from too_small_segments, and every segment removed there is counted in the number hidden shown on the alert. Whole-word hits before hiding, summed over the trend alerts: top_segments 4, dimension_totals 10, too_small_segments 65, every other field 0. The pinned file is unchanged.
- A8 (2026-10-21, amends step5.alerts.trend_knowable_at_2016_11_01): the registered value 7 was wrong; under the unchanged rule (week start + 37 days on or before the store's date) the pinned file gives 6 at 2016-11-01; cp7 (week 2016-09-26) is knowable from 2016-11-02.

## Notes

- The group that the registered statement above says is never shown as a reason is listed as a reason in 11,368 rows of Phase 4's reasons.parquet (2016-10-01 and 2016-11-01); that file, Phase 4's docs and its phrases file are left as they are (amendment A3).
- The three derived strings are the December 2016 withheld code "2016-12 not explained", the warning "data warning about the 2016-12-05 missing-renewal day" and the status "scored"; they are taken by fixed patterns from the contract's descriptions in src/retention/api/labels.py, not registered verbatim.
- POST /score scores each customer together with a placeholder copy of the row and returns only the customer's own answer. This is a workaround that relies on NumPy's summation behaviour, chosen after the exact-equality test failed, not a fix of its source: Phase 7's expected-days sum adds a one-row array in another order than an array of several rows (D-199).
- The test that recomputes the knowable count from the pinned alerts file skips in CI, because the pinned file is not in git; it runs where the file exists and checks amendment A8's count.

## Amendments A9 and A10

- A9 (2026-10-21, amends streaming.pass_marks.feature_parity): feature parity is judged on 61 columns; 7 metadata columns are excluded because they cannot be rebuilt from rows dated before the store's date. The registered wording: not met as written (mis-specified before any run).
- A10 (amends step8.http_score_parity): found after a result (D-243, D-244); registered before any A10 code or run. HTTP parity is judged with every non-float field exact and every float within relative 1e-12. The registered wording: not met as written (996 of 1,000 bodies equal as strings at 224f672, D-243). A last-bit gap could in principle flip a threshold (a reason's ranking, the chosen action, a flag) for customers outside the sample; discrete fields stay exact under A10, so such a flip inside the sample would fail it; outside the sample it is not observed.

## Notes on the stack and the runs

- The throttled replay took 816.8 s and peaked at 2.145 GB, against 550.6 s and 1.671 GB at full speed; it started 6 minutes after a restart of the Mac, so these figures are not comparable; determinism compares the table hash only.
- The python:3.11.17-slim-bookworm tag was rebuilt on 2026-10-21 at 01:20 UTC, hours before it was pinned by digest; the pin freezes that build.
- ps showed the Docker VM process at 9.83 GB resident, above the VM's 7.75 GiB, while free memory read 74% and swap 0 (D-238); unexplained and unverified.
- The API image is listed at 1.47GB by docker images and at 322,050,115 bytes by docker image inspect (D-238); the two sizes are not reconciled and unverified.
- The latency figure is for this Mac only, over loopback, with one client and one connection; the 100 ms threshold is the user's unvalidated choice.
- The HTTP score parity compares the container and the host running the same scoring code; it shows the HTTP path and the container's environment add no difference, not that the scoring is right (steps 4 and 6 cover that).
- The API container's memory limit is 1.5GiB, the user's choice; Valkey has no limit.

## Choices not registered

- /health carries a reason field beside the registered fields.
- msno must be a non-empty string; as_of must be written YYYY-MM-DD.
- A 422 body never returns the validation details, so no field name a caller sent comes back.
- Unknown paths and methods keep the framework's "Not Found" and "Method Not Allowed" bodies.
- Every /health, /score, /at-risk, /alerts, /summary and /plans call hashes the downloaded model files and the four pinned files again; /model hashes the model files only.
- A pinned file that differs after startup is named in the /health reason.
- /summary reuses the /at-risk index (the three stored rankings) for its buckets and its top 1,000.
- Startup refuses loaded model files that differ from the bundle the response schemas register.
- The /at-risk auto_renew filter takes on or off; in_plan takes true or false.
- An in_plan filter on a date without a plan is a 422.
- Each /at-risk row shows the customer's auto_renew.
- The /at-risk header counts list only the stored outside-population codes.
- /alerts takes no parameters.
- Cancel events are read as objects with msno and date; the replay must write that form.
